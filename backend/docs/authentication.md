# Authentication and authorization

## Run locally

Start PostgreSQL with `docker compose up -d postgres` from the repository root.
In `backend`, copy `.env.example` to `.env` if needed (do not overwrite your
existing database settings). Set JWT_SECRET to a random secret generated by:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Then run:

```sh
npm ci
npm run db:deploy
npm run db:seed
npm run start:dev
```

Use `npm.cmd` in PowerShell if `npm.ps1` is blocked. Keep `.env` untracked.
Startup fails immediately if required configuration is missing or invalid.

| Variable | Meaning |
| --- | --- |
| DATABASE_URL | Required PostgreSQL connection URL |
| JWT_SECRET | Required non-placeholder signing key, at least 32 characters |
| FRONTEND_ORIGIN | Required exact origin, e.g. `http://localhost:5173`; no trailing slash |
| NODE_ENV | `development` by default, or `test` / `production` |
| PORT | API port, default `3000` |
| JWT_TTL_SECONDS | Session lifetime, default `3600`, maximum `86400` |
| LOGIN_RATE_LIMIT | Login requests per client IP per minute, default `10` |

Production requires an HTTPS frontend origin and sets Secure on the cookie.
Development uses HTTP on localhost. Frontend/API deployment must remain same-site
for the SameSite=Lax cookie; arbitrary cross-site cookie deployment is out of scope.

## API contract

| Endpoint | Successful result | Access |
| --- | --- | --- |
| `GET /api/health` | `200 {"status":"ok","database":"connected"}` | Public; queries the database |
| `POST /api/auth/login` | `200 {"user":{...}}` plus a session cookie | Public; trusted Origin required |
| `GET /api/auth/me` | `200 {"user":{...}}` | Valid session cookie required |
| `POST /api/auth/logout` | `204` plus an expired session cookie | Trusted Origin required; works even without a valid session |

Login JSON contains exactly `username` and `password`. Usernames are trimmed and
lowercased; passwords are not trimmed. Extra fields are rejected. User responses
contain `id`, `username`, `name`, `role`, `classId`, `className`; never password hashes or tokens.

Errors: 400 invalid input; 401 wrong credentials/missing or invalid session;
403 untrusted Origin/insufficient role; 429 login limit exceeded. Unknown usernames
and wrong passwords return the same error, and both execute password verification.

## Test manually in PowerShell

Run the API in one terminal. In a second terminal:

```powershell
$atcBase = 'http://localhost:3000/api'
$atcHeaders = @{ Origin = 'http://localhost:5173' }
Invoke-RestMethod "$atcBase/health"
Invoke-RestMethod -Method Post -Uri "$atcBase/auth/login" -Headers $atcHeaders -ContentType 'application/json' -Body '{"username":"s10a-01","password":"AtcDemo2026!"}' -SessionVariable atcSession
Invoke-RestMethod "$atcBase/auth/me" -WebSession $atcSession
Invoke-RestMethod -Method Post -Uri "$atcBase/auth/logout" -Headers $atcHeaders -WebSession $atcSession
Invoke-RestMethod "$atcBase/auth/me" -WebSession $atcSession
```

The final request should return **401**. Teacher/admin credentials are listed in
[the seed documentation](../prisma/data/README.md). Teacher/admin quiz management
is available as documented in [quiz-management.md](quiz-management.md).
Student attempts and results are subsequent stages; login supports all roles.

Browser requests should use `credentials: 'include'`. Browsers send the Origin
header automatically. Postman/curl/PowerShell must explicitly supply
`Origin: http://localhost:5173` on POST/PUT/PATCH/DELETE requests, matching
FRONTEND_ORIGIN. Missing, `null` and untrusted origins are rejected to protect
cookie-authenticated writes, including login/logout, from CSRF.

## Implementation boundaries

- JWT is stored only in `atc_session`, with HttpOnly, SameSite=Lax, Path=/api and a
  lifetime matching token expiry. It is not returned in JSON or read from a bearer
  header. Authentication responses are marked `Cache-Control: no-store`.
- JWT verification pins HS256, issuer `atc-quiz-platform`, audience `atc-web` and
  requires an expiry and UUID subject. Roles come from the database on each
  authenticated request. Deleted users and role changes take effect immediately.
- Logout removes the browser cookie. This MVP uses stateless tokens: it does not
  revoke a copied token before its expiry. There is no refresh-token flow yet.
- Global guards protect routes by default. Mark explicitly public routes with
  `@Public()`; constrain roles with `@Roles('TEACHER', 'ADMIN')`, etc. Admin does
  not implicitly bypass role restrictions. Quiz services additionally enforce
  resource ownership; role guards alone do not grant access to another teacher's quiz.
- Login throttling uses in-memory per-IP counters, suitable for this single
  process MVP. Restarting the process resets counters. The app does not trust
  X-Forwarded-For; a future reverse-proxy deployment must configure trusted proxies
  deliberately and may need shared rate-limit storage.
- Prisma connects on application initialization and disconnects on shutdown.

## Feature tests

All test commands use verbose output so each scenario is shown by name.

| File | What it verifies |
| --- | --- |
| `test/auth-login.e2e-spec.ts` | Login for each role, safe response/cookie, invalid credentials and DTO validation |
| `test/auth-session.e2e-spec.ts` | Current user, token expiry/tampering/claims, browser logout |
| `test/auth-roles.e2e-spec.ts` | Default protection, role access matrix, current database roles |
| `test/auth-security.e2e-spec.ts` | Trusted origins, CORS, production cookies, rate limiting and health |
| `src/config/environment.spec.ts` | Startup configuration validation |
| `src/common/security/password-hashing.spec.ts` | Salted password hashing and verification |
| `src/data/csv-validation.spec.ts` | CSV syntax, fields and references |
| `test/csv-import.db-test.ts` | Transactional import, concurrency, idempotency and rollback |

```sh
npm run typecheck
npm test
npm run test:e2e
npm run test:db
npm run lint
npm run build
```

To run just one feature:

```sh
npm run test:e2e -- test/auth-login.e2e-spec.ts
```

E2E tests use the real Nest pipeline and PostgreSQL, with a separate temporary
`atc_auth_test_...` schema for each test app. They use TEST_DATABASE_URL if supplied,
otherwise DATABASE_URL, and never reset development data. Role-test routes are
defined only in test fixtures and do not appear in the real application.
